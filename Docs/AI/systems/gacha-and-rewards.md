# Gacha and rewards

Parent: [`../architecture.md`](../architecture.md). Every flow that grants or spends currency or units outside building/artifact costs: the ticket gacha ("모험가 길드" contract pages), stage-clear rewards, the mail box and notice box, and rewarded ads.

## How it works

**Currencies.** Economy currency ids live in `Constants` (`Assets/Scripts/DB/Constants.cs`): `GOLD`, `WOOD`, `IRON`, `TICKET`, `MAGICSTONE`, `BM`, mapped to `ResourceType` by `BackendManager.EconomyEnumToId`/`EconomyIdToEnum`. `ResourceType.Food` (battle-only, never saved) and `ResourceType.EXP` (player EXP lives in `PlayerSaveData.PlayerExp`) are not Economy currencies. Truth = UGS Economy. `PlayerDataManager._resources` is a cache filled by `InitializeResourcesAsync` → `BackendManager.LoadEconomyData` at boot (and again from `BackendManager.CheckInterentAsync` when you come back to the start screen). UI listens to the C# event `PlayerDataManager.OnResourceChangedEvent` (not EventManager).

**Changing currency (`PlayerDataManager.AddResource(type, amount)`).** It is optimistic: it updates `_resources` first (clamped to 99999, with no lower bound), fires `OnResourceChangedEvent`, then (except Food) awaits `BackendManager.ChangeEconomyAsync(id, amount)`. That call goes through the queue to Cloud Code `Economy.ChangeEconomyResource`, which increments or decrements by `|amount|` (0 returns immediately). A 422 (insufficient funds) makes `InternalChangeEconomyAsync` reload balances, call `PlayerDataManager.SyncAllResources`, and throw `"NOT_ENOUGH_FUNDS"`. `ExecuteWithRetryAsync` shows a "재화가 부족하여" (insufficient currency) popup and rethrows. No other failure rolls the local value back. `ChangeResourceOnlyLocal(type, value)` *sets* (not adds) the local value. The gacha uses it with the balance the server returns.

**Gacha request path.**
1. Entry: `UIMenu.OnGachaBtnClicked` (fires `GachaModuleV2Bindings.WakeUpServer()` without awaiting it, outside the queue) or `DiplomacyPanel.OnAdventurerGuildClicked`. Both `FadeManager.SwitchGameObjects` to the `GachaUIPanel` that `UIManager.GetUI` already loaded.
2. `GachaUIPanel.OnEnable` sets pull buttons from the local ticket count (≥1 / ≥10) and pity labels from `PlayerDataManager.LimitedGachaPityCount`/`StandardGachaPityCount` over the static `LimitedGachaPityLimit`/`StandardGachaPityLimit`.
3. `OnPullOneClicked`/`OnPullTenClicked`: local ticket pre-check → page 0 calls `BackendManager.OnePickupGachaAsync`/`TenPickupGachaAsync` (banner `Constants.PICKUP_GACHA_KEY` = `"PICKUP_BANNER"`), page 1 calls the Normal variants (`"NORMAL_BANNER"`). The client never deducts tickets itself.
4. Server `GachaModuleV2.PerformGachaDraw`: load banner config (Remote Config key `GACHA_BANNERS` → `gachaBanners.<bannerId>`, cached in a static for the worker's lifetime) → read pity from Cloud Save `PITYCOUNT_<bannerId>` → Economy virtual purchase `ONE_GACHA`/`TEN_GACHA` (spends TICKET; the purchase definitions live in the Economy dashboard config, not in the repo) → roll N times → read TICKET balance → write pity → return `GachaResult { ResultUnit[{UnitId, Rarity}], CurrentPityCount, UserCurrency }`. If the balance read or the pity write fails, it returns `UserCurrency = -1`.
5. Client checks: an empty list (or not exactly 10 for a ten-pull), or `UserCurrency == -1`, throws, and nothing is applied. Otherwise it calls `gachaSequenceController.StartGachaSequence(ids)`, then `PlayerDataManager.UpdateLimitedPityCount`/`UpdateStandardPityCount(CurrentPityCount)` (publishes `LimitedPityCountUpdatedEvent`/`StandardPityCountUpdatedEvent`, which `GachaUIPanel` subscribes to), `ChangeResourceOnlyLocal(Ticket, UserCurrency)`, and `UnLockUnit(id)` for each result (adds to `OwnedCardData` or bumps `ownedCount`, fires `OnUnitCountChanged`).
6. `finally`: re-evaluate buttons, `HideLoading`, `await PlayerDataManager.SaveDataToCloudAsync()`. This is what persists the new units (`PlayerSaveData.OwnedCardData`/`CardCounts`).
7. Sequence: envelope `VideoPlayer` (tap to play, skip allowed) → `OnEnvelopeAnimationFinished` builds the grid (epics pre-flipped) and queues every epic for a full-card reveal → grid; skip flips the rest; confirm closes. "Epic" here is the **local** `DataManager.PlayerUnitData` `rarity == Rarity.epic`. The server's `ResultUnit.Rarity` is ignored.

**Pity and rates are server-only** (Remote Config + GachaV2). Per draw: `pity++`. If `pity >= PityThreshold`, the unit is `GuaranteedItemId`, or a random Epic id when it is `-1` (the normal banner). Otherwise weighted `SelectRarity` over `RarityTable` weights. On the pickup banner (`GuaranteedItemId != -1`), an Epic roll is the pickup unit 50% of the time, and otherwise a random id from the Epic list, which may also be the pickup unit. Reset to 0: normal banner, on any Epic or at pity. Pickup banner, only when the pickup unit is obtained. The client only displays pity. `GetGachaBanners` returns `{BannerId, PityThreshold}` and is called inside `BackendManager.InternalLoadDataAsync` to build the pity keys and fill `AllCloudData.NormalPityThreshold`/`PickupPityThreshold`. The 140 "warning" color threshold is a serialized field on `GachaUIPanel` (`pityWarningThreshold`), independent of the server threshold.

**Stage rewards.** `GameManager.ShowResultUI(true)` computes gold/wood/iron/magic stone client-side (`DataManager.RewardData` + building effects + `Modifiercalculator.GetRewardMultiplier`), opens `RewardPanelUI.OpenUI(gold, wood, iron, magicStone, isVictory, exp)` **before** granting, then runs four `AddResource` calls in parallel (`UniTask.WhenAll`) and `SaveDataToCloudAsync`. Defeat: `PlayerDataManager.ApplyResourcePenalty` (−5% each) and a negative display. `GameManager.ClearStage` → `PlayerDataManager.MarkLocalStageClear`, which grants `AddResource(Ticket, 10)` on first clear of stage 1-2.

**Mail and notices.** Source: Remote Config JSON arrays, key `GLOBAL_MAIL_LIST` (mail) and `NOTICE_LIST` (notices), shape `PublicMailData {id, title, body, rewards[{itemId, amount}], expirationDate}`. Mails are global, not per player. `UIMenu.OnEnable` calls `CheckNewMail(false)` on its two serialized `PostBox`es (`mailOrNotice` = `isMail`/`isNotice`). The fetch is throttled to 600 s via `BackendManager.LastPostFetched`. It fetches the list (`CheckMailAsync` → `RemoteConfigService.FetchConfigsAsync`), loads the claimed-id list from Cloud Save (`ALREADY_RECIEVED_MAIL` / `ALREADY_RECIEVED_NOTICE`), hides expired entries (`DateTime.Now` vs `expirationDate`), and shows unread counts with `UIMenu.DisplayNewPost`/`DisplayNewNotice`. Claim (`PostContent.OnRewardButtonClickAsync`): one `AddResource` per reward in parallel → `PostBox.OnRewardRecieved(id)` appends the id and `SaveDataAsync`s the whole list → `CheckNewMail(true)`. Opening an unread notice row also calls `OnRewardRecieved` (marks it read).

**Rewarded ads.** `BackendManager.WatchAdAndGetReward()` (connectivity check → `AdManager.ShowRewardedAdAsync()`) has one caller: `UIStageClearArtifactSelect.OnRerollButtonClicked` (artifact reroll). Two others bypass `BackendManager` through the legacy callback `AdManager.Instance.ShowRewardedAd(onReward)`: `ConstructionUpgradePanel.OnAdRepairButtonClicked` (instant repair) and `MainScreenBuildingController.ConfirmAdAndMove` (−30 cooldown and move). No ad grants currency. Server-side verification exists (`AdManager.ServerSideVerification`) but is never called. `AD_UNIT_ID` is always the Google test id (`#if true`).

## Data and persistence
| Data | Where | Written by |
|---|---|---|
| Currencies GOLD/WOOD/IRON/TICKET/MAGICSTONE/BM | Economy | Cloud Code `ChangeEconomyResource` (client-chosen amount) and `ONE_GACHA`/`TEN_GACHA` virtual purchases |
| Local currency cache | `PlayerDataManager._resources` | boot load, `AddResource`, `ChangeResourceOnlyLocal`, `SyncAllResources` |
| Pity per banner | Cloud Save `PITYCOUNT_NORMAL_BANNER`, `PITYCOUNT_PICKUP_BANNER` | server only (GachaV2). Client mirrors: `StandardGachaPityCount` (normal, page 1), `LimitedGachaPityCount` (pickup, page 0) |
| Banner config, rates, pity threshold | Remote Config `GACHA_BANNERS` (read by Cloud Code) | dashboard |
| Owned units from gacha | Cloud Save `PLAYER_DATA` (`PlayerSaveData.OwnedCardData`, `CardCounts`) | client `SaveDataToCloudAsync` (full overwrite; skipped while `!GameManager.IsTutorialCompleted`) |
| Mail/notice content | Remote Config `GLOBAL_MAIL_LIST`, `NOTICE_LIST` | dashboard |
| Claimed mail / read notice ids | Cloud Save `ALREADY_RECIEVED_MAIL`, `ALREADY_RECIEVED_NOTICE` (`List<string>`) | `PostBox.OnRewardRecieved` |

## Common changes
- **Add a currency:** 1. Create it in the Economy dashboard. 2. Add a `Constants.*_ID` and a `ResourceType` value (append it; don't reorder, the enum may be serialized). 3. Add both switch cases in `BackendManager.EconomyEnumToId`/`EconomyIdToEnum`. An unmapped Economy id makes `InternalLoadEconomyData` throw, so boot-time currency loading fails. 4. For mail rewards, add cases in both `PostContent` switches and a `postRewards` slot in the prefab (the index order is GOLD, WOOD, IRON, TICKET, MAGICSTONE, BM). 5. Add a label in `ResourceUI`/`BmResourcePanel` if it should be shown.
- **Change rates, pool, pity, or the pickup unit:** edit Remote Config `GACHA_BANNERS`. No code change is needed, but the Cloud Code worker caches the config statically, so a change may not apply until the worker restarts. Every `GuaranteedItemId` must also appear in some `RarityTable[].IDs`, or the draw throws after the tickets are spent. New unit ids must exist in `DataManager.PlayerUnitData`/`PlayerDataManager.AllCardData` (checked by `UnLockUnit`).
- **Add a banner:** the client hard-codes two banners (the two `Constants.*_GACHA_KEY` values, the page index mapping in `GachaUIPanel`, two pity fields, and the two keys in `InternalLoadDataAsync`). You need a new constant, a page, BackendManager wrappers, a pity field and event, and the load code.
- **Send a mail:** append an entry with a globally unique, never-reused `id` to `GLOBAL_MAIL_LIST`. Always include a `rewards` array (use `[]` for notices). Use `itemId`s from the `Constants` currency ids only.
- **Change a GachaV2/Economy signature:** redeploy the module, then regenerate `Assets/CloudCode/GeneratedModuleBindings/`. The `.sln`/`.csproj` files are gitignored and the `.ccmr` paths are Windows-style (`..\\..\\..\\GachaV2\\GachaV2.sln`).

## Gotchas
- **What the client trusts.** The gacha is server-authoritative only for the ticket charge, the roll, and pity. The resulting units are granted by the client and saved in `PLAYER_DATA`, which the client writes wholesale, so ownership is not enforced. `ChangeEconomyResource` accepts any currency and any amount from the client ("보안 우려가 있음", i.e. a security concern, per the comment on `ChangeEconomyAsync`). Stage rewards, mail rewards, and the claimed-mail list are all client-decided.
- **Retry semantics.** `CloudCodeException` and `EconomyException` derive from `RequestFailedException`, so any Cloud Code error, including server-side rejections such as "not enough tickets" in the virtual purchase or a bad banner id, shows the "네트워크 오류… 다시 시도하시겠습니까?" (network error, retry?) popup. Retry re-sends the same request. Cancel runs `HandleUserCancel` (loads StartScene, or quits on the start screen) and throws `OperationCanceledException`. Only `ChangeEconomyAsync`'s 422 maps to the insufficient-currency popup.
- Suspected issue (gacha, grant lost): if the response is lost after the server's purchase succeeded (timeout, app killed), tickets and pity are consumed but no unit is granted. Pressing Retry performs a *second* paid draw. There is no idempotency key.
- Suspected issue (gacha, grant lost): when the server returns `UserCurrency == -1` (balance read or pity write failed after the purchase), `GachaUIPanel` throws and discards the rolled units even though the tickets are spent. A config exception after the purchase (the `RarityTable.First(...)` lookup for `GuaranteedItemId`, or no Epic ids at pity) also charges without a result.
- Suspected issue (gacha, grant lost): units exist only locally until `SaveDataToCloudAsync` succeeds. It swallows exceptions and is a no-op while `GameManager.IsTutorialCompleted` is false, so a failed save followed by an app kill loses the pulled units.
- Suspected issue (every `ChangeEconomyAsync` grant, double grant): Cloud Code increment is not idempotent. If a timeout/`RequestFailedException` arrives after the server applied it and the player taps Retry, it is applied twice (and a local `+amount` was already applied once). On a failure or a cancel, the optimistic local change is never rolled back, so the local and server values diverge until the next `LoadEconomyData`.
- Suspected issue (mail, double grant): grants and the claim record are not atomic. If the rewards succeed and `SaveDataAsync` of the claimed list fails (or the app dies), the mail stays claimable. With several rewards, one failed `AddResource` re-enables the button while the others already succeeded, and re-claiming grants those again. An unknown `itemId` `return`s mid-loop after earlier `AddResource` tasks already started, so those are granted and the mail is never marked claimed.
- Suspected issue (mail): expiry uses device `DateTime.Now` (the clock can be changed) and `DateTime.TryParse` in the device culture. `ProcessMailData` logs `rewards.Count`, so an entry without `rewards` throws a NullReferenceException, and the catch returns 0 with the rest of the list unrendered. `InternalCheckMailAsync` swallows every exception and returns null, so the queue's retry never applies to mail.
- Suspected issue (stage 1-2 ticket, double grant): `MarkLocalStageClear` awaits the Economy grant before `ClearStage` unlocks the next stage and saves. A failed save or a kill in between leaves the stage uncleared on reload, so it can be re-cleared for another 10 tickets.
- Suspected issue (ads): `WatchAdAndGetReward` discards the `bool` from `ShowRewardedAdAsync`, so the artifact reroll happens even when the ad was not ready, not initialized, or closed early. On WebGL `ShowRewardedAdAsync` always returns true. `ConfirmAdAndMove` calls `SaveDataToCloudAsync` right after starting the ad, before the reward callback.
- Suspected issue (pity display): in `BackendManager.InternalLoadDataAsync`, the "no pickup pity key" branch sets `cloudData.NormalPity = 0` instead of `PickupPity`, which wipes a loaded normal pity from the display. It is display only; the server count is correct. That method also logs the key with the prefix applied twice.
- Gacha config is on the boot path: `InternalLoadDataAsync` calls `GetGachaBanners` first, so a GachaV2/Remote Config failure blocks the whole `PLAYER_DATA` load: a `CloudCodeException` first shows the queue's retry popup, and if the player cancels (back to StartScene) or the error is not a `RequestFailedException`, the load fails (`LoadDataFromCloundAsync` only logs it).
- The `EconomyException` Conflict branch in `ExecuteWithRetryAsync` and the `writeLocks` dictionary are effectively dead. All writes go through Cloud Code, and `writeLocks` is filled but never read.
- `RewardPanelUI` stays active at alpha 0 so that `Awake` can register it in `GameManager.RewardPanelUI`. Its `CloseUI` override hides it **and loads MainScene**. It shows amounts before the grant runs, and whatever the grant's outcome.
- Two `Rarity` enums: the game's `Rarity` (`common, rare, epic, Legendary`, in `BaseUnitData.cs`) and the generated `Unity.Services.CloudCode.GeneratedBindings.CheerUpMyHero.CloudCode.Rarity` (`Epic, Rare, Common`). `GachaUIPanel` imports the generated namespace, but an unqualified `Rarity` resolves to the global one.
- Naming: "Limited" = pickup = page 0 = `PICKUP_BANNER`. "Standard" = normal = page 1 = `NORMAL_BANNER`.
- Dead code: `GachaUIPanel.GetForcedEpicResult`/`IsResultEpic` (old client-side pity with hard-coded ids), `PlayerDataManager.LoadPityCounts`, `GachaPageChangedEvent` (published, no subscriber), `ContractPagesController.ShowLimitedCharacterDetails`/`ShowStandardCharacterDetails` (log only), `AdManager.ServerSideVerification`, and the legacy Gacha/, Gatcha/, HelloWorld/ modules. Gacha/ still has `Gacha.ccmr` and bindings `GachaModuleBindings`/`MyModuleBindings` that no code calls.
- Minor: `OnPullOneClicked` returns before its `try` when `gachaSequenceController` is null, so the loading overlay stays up. Each pull disables only its own button, so both pulls can be queued at once and the second sequence replaces the first on screen (both grants apply). The pull buttons don't react to ticket changes while the panel is open. `LastPostFetched` is shared by the mail and notice boxes.
